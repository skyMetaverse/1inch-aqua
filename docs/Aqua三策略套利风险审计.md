# Aqua 三策略套利风险审计

## 结论

本记录针对同一 maker 的 `1INCH/USDT` 三策略组合进行只读核验。目标组合为：

- 双边策略：`1INCH 100% + USDT 100%`，每侧区间 `0.15%`。
- 上单边策略：`1INCH 100%`，区间 `0.15%`。
- 下单边策略：`USDT 100%`，区间 `0.15%`。

已确认的结论如下：

1. 三条策略会把同一 maker 的每种资产各登记两次虚拟额度：双边与上单边共同登记 `1INCH 100%`，双边与下单边共同登记 `USDT 100%`。这不是两次立即 ERC20 转账，但会使合计 virtual balance 超过钱包余额。
2. 虚拟额度重叠不会让 taker 从 maker 钱包提取超过真实余额；后续 `pull()` 无法被钱包余额和 allowance 覆盖时，交易会失败。这是 `illiquidity`、部分成交后退款或重挂的直接风险，不是免费资金来源。
3. 独立重挂后的策略中心价格不同，会让单边和双边区间发生重叠并形成内部正向循环报价。固定区块的真实 `quote` 已测得小额正毛利，但当时的最大毛利远小于 Ethereum 主网 gas，因此**未确认存在当前可盈利的实际套利交易**。
4. 在同一批次对 Uniswap V3 `0.3%` 池做的两腿报价中，未找到 `Aqua -> Uniswap -> Aqua` 之外的单市场可盈利循环；该结果不能证明所有 DEX、聚合路由或私有订单流都不存在套利路径。

结论必须限定在本次区块、测试规模、当前策略快照和指定外部池。策略、余额和价格会被运行中的 Bot 持续更新，不能把本记录的负盈利结果延伸为永久安全保证。

## 审计边界

本次只执行只读请求：

- 官方策略 API：读取 maker 的 open 策略和 `strategyBytes`。
- 公共 Ethereum RPC：`eth_call`、`eth_getBalance` 等只读调用。
- SwapVM 官方 SDK：对每条策略编码 `quote()` 并以 `eth_call` 执行。
- Aqua registry：读取每条策略每个 token 的 `rawBalances`。
- Uniswap V3 Quoter V2：对 `1INCH/USDT` `0.3%` 池进行 `quoteExactInputSingle`。

未读取 `.env`，未解密私钥，未广播交易，未调用 `swap()`，未向任意账户申请授权。

## 已确认的资金承诺风险

### 配置层的重叠

当前本地 `config/lp.add.jsonc` 的三条策略使用以下资产比例：

| 策略 | 1INCH 虚拟额度 | USDT 虚拟额度 |
| --- | ---: | ---: |
| 双边 | 钱包余额的 100% | 钱包余额的 100% |
| 上单边 | 钱包余额的 100% | 0% |
| 下单边 | 0% | 钱包余额的 100% |
| 合计 | 钱包余额的 200% | 钱包余额的 200% |

Aqua SDK 对 `ship()` 的定义是“设置策略虚拟 token 余额”，不是将 ERC20 转入 registry，见本地 [Aqua SDK README](../node_modules/@1inch/aqua-sdk/README.md) 的 `Ship` 说明。项目也在 `ship` receipt 后读取 registry `rawBalances`，见 [add-lp.ts](../src/app/add-lp.ts)。

因此，三策略同时登记成功不代表每种 token 都有两倍真实资金。它表示同一钱包资产被两个策略共享承诺。若两个策略在相近时间都需要向 taker 交付同一种 token，前一笔已执行的 `pull()` 会减少 maker 钱包余额，后一笔可能因余额或 allowance 不足而回滚。该后果是报价深度不可靠、`illiquidity`、失败成交或 Bot 重挂，不是协议允许超额转走资产。

### 链上快照验证

在区块 `25786849`，对当时 API 返回的相关 open 策略读取 registry `rawBalances` 并读取 maker ERC20 钱包余额，得到：

| 项目 | 1INCH raw | USDT raw |
| --- | ---: | ---: |
| maker 钱包余额 | `28845282550392601931827` | `7573405325` |
| 各策略 virtual balance 合计 | `61305940547708509474166` | `626617942` |
| 钱包 / virtual 合计覆盖率 | 约 `47.05%` | 约 `1208.61%` |

该时点的 1INCH 虚拟承诺确实超过真实钱包余额两倍附近。此项是已确认的共享流动性风险，且与 Bot 观察到 `illiquidity` 后停止旧策略、再按钱包余额重挂的行为一致。

## 什么情况下会被套利

### 外部市场套利

对任意 Aqua 策略，令：

```text
P_aqua_buy  = 用 USDT 在 Aqua 买入 1INCH 的有效价格
P_aqua_sell = 在 Aqua 卖出 1INCH 得到的有效价格
P_ext_buy   = 在外部市场买入 1INCH 的有效价格
P_ext_sell  = 在外部市场卖出 1INCH 得到的有效价格
```

在扣除两侧手续费、滑点、gas、MEV 保护成本后，满足任一条件才会有经济套利：

```text
P_aqua_buy < P_ext_sell
P_aqua_sell > P_ext_buy
```

集中流动性天然会发生这种情况：外部价格变化后，套利者会交易 Aqua 策略，直到策略曲线的边际价格接近外部可执行价格，或该方向虚拟余额耗尽。对 LP 来说，资产由表现较强的一侧向表现较弱的一侧转换是正常的 adverse selection / 无常损失暴露，不是三策略组合独有的合约漏洞。

本项目的 `0.15%` 单边宽度、`0.15%` 双边半宽和 `0.03%` 重挂额外偏离，不会消除这个风险。它们只定义 Bot 何时停止旧策略、按新 current 建立新策略。价格快速跳变、Bot 轮询间隔、三次连续确认、冷却期和交易落链之间，旧曲线仍可以被外部成交或套利。

### 三策略内部交叉套利

如果两条策略独立重挂到不同 current，可能出现：

```text
策略 A：1INCH -> USDT 的有效报价较高
策略 B：USDT -> 1INCH 的有效报价也较高
```

若将两条 quote 首尾相接，且两条策略的输出 virtual balance、maker 钱包余额及 allowance 都能覆盖，就会产生内部循环：

```text
1INCH -> 策略 A -> USDT -> 策略 B -> 1INCH
```

或相反方向：

```text
USDT -> 策略 A -> 1INCH -> 策略 B -> USDT
```

初始三策略在完全相同的 current 下建立时，单边与双边的价格边界理论上对齐；不能仅凭“有两个单边加一个双边”断言一定有正循环。风险来自之后的独立重挂、部分成交、不同中心价格和重叠区间，而不是策略数量本身。

## 实际 quote 测试

### 方法

使用 `@1inch/swap-vm-sdk` 的 `SwapVMContract.quote()` 生成 calldata，再通过公共 Ethereum RPC 对 Aqua SwapVM 合约执行固定区块 `eth_call`。这与 SDK README 中推荐的 quote 流程一致，见本地 [SwapVM SDK README](../node_modules/@1inch/swap-vm-sdk/README.md)。

每个候选路径额外校验：

1. 第一笔 quote 的输出不超过第一条策略该输出 token 的 `rawBalances`。
2. 第二笔 quote 的输出不超过第二条策略该输出 token 的 `rawBalances`。
3. maker 的 ERC20 钱包余额覆盖测试规模。

这能排除仅有价格输出、但策略没有可交付 token 的伪路径。它仍不是自定义原子套利合约的完整 `swap()` 交易模拟，因此不能替代真实执行审计。

### 内部循环测试结果

区块 `25786872` 的 API/链上快照中，存在两个 1INCH 单边策略和一个 USDT 单边策略。相关虚拟余额为：

| 策略角色 | 1INCH raw | USDT raw |
| --- | ---: | ---: |
| 1INCH 单边 A | `19938068609567780699947` | `0` |
| 1INCH 单边 B | `19938068609567780699947` | `0` |
| USDT 单边 | `0` | `2739294` |

其中一个 1INCH 单边区间为 `0.083063581608167810 - 0.083188176980287505`，USDT 单边区间为 `0.083049248012268339 - 0.083090793408704263`。两者存在重叠，且实际 quote 出现小额正循环：

| 输入 1INCH | 第一腿 USDT 输出 | 第二腿 1INCH 输出 | 毛利 1INCH |
| ---: | ---: | ---: | ---: |
| `1` | `0.083089` | `1.000293934699809731` | `0.000293934699809731` |
| `5` | `0.415434` | `5.001336492948409719` | `0.001336492948409719` |
| `10` | `0.830836` | `10.002297898380113670` | `0.002297898380113670` |
| `20` | `1.661547` | `20.003095448380693535` | `0.003095448380693535` |
| `30` | `2.492131` | `30.002356536546240443` | `0.002356536546240443` |

这是一个**已确认的 quote 级别正价差**。它证明独立重挂后区间重叠可形成内部价格倒挂。

但在该区块，以约 `0.083 USDT / 1INCH` 估算，最大的 `0.003095 1INCH` 毛利约为 `0.00026 USDT`。它远低于一次主网两腿交易所需 gas。因此该时点的路径没有经济执行价值，不能称为“当前可盈利套利”。

### 外部 Uniswap V3 对照

在区块 `25786877`，使用 Uniswap V3 Quoter V2 的 `1INCH/USDT` `0.3%` 池，针对相同策略做两腿测试：

| 路径 | 测试输入 | 最终结果 |
| --- | ---: | ---: |
| Aqua 卖 1INCH -> Uniswap 买回 1INCH | `1 1INCH` | 净亏 `0.015635229848354115 1INCH` |
| Aqua 卖 1INCH -> Uniswap 买回 1INCH | `20 1INCH` | 净亏 `0.616292395894955743 1INCH` |
| Aqua 买 1INCH -> Uniswap 卖回 USDT | `1 USDT` | 净亏 `0.000613 USDT` |
| Aqua 买 1INCH -> Uniswap 卖回 USDT | `2 USDT` | 净亏 `0.020938 USDT` |

在这个指定池、指定区块和规模中，没有发现外部可盈利循环。

## 当前确定存在的问题

### 1. 每种资产 200% 的虚拟承诺

这是配置确定产生的结果。它会让实际可执行深度小于多个策略 virtual balance 的合计，并在市场快速成交时产生 `illiquidity` 或后续 `pull()` 失败。该问题不能通过增加区间宽度解决。

### 2. 独立重挂会让策略价格不同步

Bot 按每个 `strategyHash` 独立决定和重挂，策略不一定在同一 EMSH current 下创建。当前实测过的状态已经从预期的“一双边、两单边”变化为“两条 1INCH 单边、一条 USDT 单边”，并出现重叠区间。这是内部 quote 级别价差的直接来源。

### 3. 当前 `0.15%` 只降低重挂频率，不消除价格风险

更宽区间能降低因为短期波动触发 `dock -> ship` 的频率，但它不能阻止外部市场将策略曲线推向新的价格，也不阻止独立重挂后的区间交叉。若目标是降低内部交叉价差，关键是给同一资产共享资金的策略增加联合价格约束或限制重叠，而不是单独继续扩大区间。

## 未确认事项

以下不能基于本次测试声称已经安全或已经存在问题：

1. 未对所有 DEX、RFQ、1inch Pathfinder 路由、私有交易池和 MEV bundle 做全市场报价比较，不能证明不存在外部套利。
2. 未部署套利合约，也未广播两腿 `swap()`；内部正价差是 quote、virtual balance 和钱包余额约束共同验证的结果，不是已成交交易。
3. 未取得长期的成交、手续费、无常损失和 gas 样本，无法给出这组三策略的净收益结论。
4. 策略 API 与链上状态在 Bot 快速重挂时会有索引延迟；每次准备真实交易都应以 registry `rawBalances` 和钱包余额为准。

## 建议

1. 保留 `illiquidity -> dock -> 按钱包余额重挂`，因为它是共享虚拟额度无法被真实余额覆盖时的正确保护动作。
2. 在 Bot 面板中持续记录同 pair 策略之间的 quote 级交叉价差，至少检测 `1INCH -> USDT -> 1INCH` 与 `USDT -> 1INCH -> USDT` 两个方向，并同时记录可用 `rawBalances`、钱包余额和估算 gas。
3. 若内部循环在扣 gas 前长期为正且规模足够，应在重挂前拒绝会与同 maker 现有策略造成正循环的区间，或者将共享余额改为分配额度而非每条策略各 `100%`。
4. 若目标是保证每条策略都能被完整执行，三策略不应对同一 token 都使用 `100%`；需要为双边、上单边和下单边分配不重叠的资金比例。这样会减少 `illiquidity`，但也会降低每条策略显示的深度。
